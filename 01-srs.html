Document 01

Software Requirements Specification

Follow-Up Management System — the complete functional & non-functional requirements needed to build the platform served on port 5080.

1 · Introduction

1.1 Purpose

This document specifies the requirements of the Follow-Up Management System in enough detail to build a functionally equivalent application. It defines the system's actors, its authorization model, every functional capability grouped by module, the business rules it enforces, its data and interface requirements, and the quality attributes it must satisfy.

1.2 Scope

The system is a single-tenant, bilingual (English/Arabic) B2B client-relations and field-operations platform for a medical-laboratory group. The group's clients are other laboratories; the group's field representatives visit those client labs on scheduled rounds to collect biological samples, move them to hubs, receive them at the laboratory, and handle the surrounding commercial relationship (marketing, complaints, loyalty). The system additionally imports/synchronizes volume & revenue statistics, computes loyalty and commissions, and produces operational dashboards and management reports.

The system holds no patient orders and performs no clinical processing; it is a relations/operations system, not a Laboratory Information System (LIS). It does, however, capture some patient-identifying fields inside complaint details (see BR and §9 privacy). It provides no payment processing and uses local username/password authentication (no external identity provider).

1.4 Requirement conventions

  • FR-n — a functional requirement (a capability). BR-n — a business rule (a constraint). NFR-n — a quality requirement.
  • Priority: MUST = mandatory for parity; SHOULD = expected but with acceptable variation.
  • The verbs shall/must denote mandatory behaviour. "The system" means the backend service unless a UI is named.
  • Every FR lists its primary API routes; the full route contract is in Document 03 §API surface.

2 · Overall description

2.1 Product perspective

The product is a self-contained web application: one process serves the browser SPA and the JSON API, and owns its PostgreSQL database schema (provisioned at startup). It integrates read-only with an upstream Oracle system for reference data and statistics, and outbound with SMTP and WhatsApp gateways for notifications. It is designed to run as exactly one instance.

2.2 Product classification

  • Tenancy: non-multi-tenant. A single organization; access is bounded by organizational scope, not tenant isolation.
  • Locale: Egyptian governorates; all business-day logic runs on Africa/Cairo time. UI, templates, and notifications are fully bilingual en/ar; each user has a language preference.
  • Data sensitivity: holds personal data (staff, lab contacts) and financial data (salaries, commissions, revenue), plus patient-identifying fragments inside complaint details. See NFR-Privacy.

2.3 Operating environment

AspectRequirement

DatabasePostgreSQL 16/17. The application connects as the schema-owning role and provisions the schema on startup.
HostingEither containerized (Kestrel, non-root) or IIS in-process on Windows Server. Time zone pinned to Africa/Cairo.
ClientModern evergreen browser. The sanctioned client is a zero-build vanilla-JS SPA served from the API's static root.
Real-timeServer-Sent Events (one instance; in-memory subscriber registry).

2.4 Design constraints (inherited from the reference build)

  • Single instance: SSE subscriber registry and stream tickets are in-memory; scheduled jobs are serialized by PostgreSQL advisory locks so a second instance degrades safely rather than duplicating work. Horizontal scale-out is explicitly out of the baseline.
  • Server-authoritative: all authorization, all money computations, and all e-signature digests are computed server-side; client-supplied privileges, payout figures, and digests are never trusted.
  • Append-only audit: the audit trail is immutable at the database level (enforced by triggers, not merely by application code).

2.5 Assumptions & dependencies

  • An operator supplies secrets via environment/configuration (DB password, token-signing secret, SMTP/WhatsApp credentials, Oracle connection string). The system fails fast at startup if required secrets are missing.
  • Oracle integration is inert unless the operator provisions the Oracle managed driver and configures the connection; only three allow-listed read queries are ever executed.
  • The upstream Oracle view/query shapes are operator-configured (config-managed, not web-editable).

3 · Actors & user classes

3.1 Human actors (login users)

Roles are dynamic — defined in data, not hard-coded — each carrying a privilege array, default language/theme, and six organizational-scope arrays. The reference build seeds four roles, all at global (*) scope:

RoleReadingSeeded capability
AdminFull back-office administratorAll privileges: dashboard, labs, reps, daily follow-up (+verify), marketing, complaints (+resolve), reports, user management, lab location, encrypted-lab visibility, Oracle integration, sample tracking, outsource, setup.
OperationsManagerSupervises boards, complaints, reportsViewDashboard, VerifyDailyFollowup, ResolveComplaints, ViewReports, ViewLabLocation (+ setup/sample-tracking/outsource sets).
CollectorField collector loginViewDashboard only; operational capability comes from record ownership (their assigned labs) plus any additional grants.
MarketingField marketing loginViewDashboard only; capability via ownership + grants.

A login account may be linked to a representative record (unique: one login per rep). When linked, the account is additionally limited to records it owns (its own labs/visits). A non-linked account is an office/supervisor account not restricted by per-rep ownership.

3.2 Field workforce (domain records, not necessarily logins)

Representatives of type Collector (sample pickup), Marketing (relationship/growth), Transfer (sample transport to hub), and Scanning (lab discovery/onboarding). Reps carry employment attributes (salary, goal type, target, metric, duration Monthly/Quarterly). A rep may receive WhatsApp notifications without having a web login.

3.3 Client-lab contacts (data subjects)

Each client lab has one or more contact persons (Manager, Receptionist) with name, phone, and birthday. Birthdays drive reminder notifications. Contacts are never system users.

3.4 System actors (in-process background services)

4 · Authorization model

Authorization is enforced server-side in three layers plus a grant guard. This model is a first-class requirement — it governs every functional requirement in §5.

4.1 Privileges (representative set)

Privileges are grouped by module, typically View/Add/Update/Delete/Manage per area. Key privileges include:

ViewDashboardManageLabsAddLabsUpdateLabsViewLabLocationShowEncryptedLabs ManageRepsViewRepsAddRepsUpdateReps ViewDailyFollowupAddDailyFollowupUpdateDailyFollowupVerifyDailyFollowup ViewTransfersConfirmTransfersManageTransfers SampleTrackingOutsourceSamples ViewMarketingAddMarketingUpdateMarketing ViewComplaintsAddComplaintsUpdateComplaintsResolveComplaintsManageComplaints ManageLoyaltyManageCommissions ViewLabStatsViewTeststatsAddGroupsUpdateGroupsDeleteGroupsAddTestsetupUpdateTestsetupDeleteTestsetupAddTeststats ViewReportsManageUsersOracleIntegrationSetupRefsSetupCitiesSetupAreas

Privilege expansion rule. A coarse Manage<Area> privilege implies the fine-grained View/Add/Update/Delete for that area, and a few documented cross-grants apply (e.g. ViewReports implies ViewLabStats). Expansion is computed centrally so the UI and backend cannot disagree.

4.2 Organizational scope & record ownership

Each role/user carries six scope arrays: allowed_branches, governorates, cities, areas, categories, segments. A value of * means "all"; an empty array means "deny all" (fail-closed). Every record-bearing operation checks the record against these arrays. Where migrated, the same rule is also pushed into SQL (a WHERE filter) with the in-memory check retained as a post-filter; a divergence between the two is logged as critical.

Accounts linked to a representative are additionally constrained to records they own (their assigned labs/visits), independent of scope breadth.

4.3 Anti-amplification (grant guard)

BR-govern: No user or role write may confer a privilege or a scope breadth that the acting caller does not themselves hold. This is enforced on all four user/role write paths — create user, update user, create/update role, delete — and covers both the record's current and proposed privileges. Self-role-change is blocked; the built-in admin account and in-use roles are protected from deletion.

5 · Functional requirements

Requirements are grouped into 21 modules (FR-1…FR-21). Each states the capability, the behaviour to implement, acceptance criteria, and the primary API routes.

FR-1Authentication & sessionsMUST

A user authenticates with username + password, receives a bearer session token, and can end the session. Every non-public route requires a valid token; each operation additionally requires its privilege.

Behaviour
Passwords stored with PBKDF2-SHA256 (100k iterations, per-user salt), constant-time compare. On success, issue a signed token (HMAC-SHA256 over a compact payload; ~10-hour expiry) and create a session row. Logout marks the session revoked; the auth layer treats a revoked session as invalid on the very next request. Per-account lockout after repeated failures (default 10 fails / 15 min, configurable) plus per-IP rate limiting on login. Users may change their own password (re-authenticating with the old one; minimum length enforced).
Acceptance
(a) Valid credentials → token + session; invalid → rejected and the failure recorded. (b) Repeated failures lock the account; an admin can unlock. (c) An unauthenticated request to any /api/* route except the declared public ones → 401. (d) A request lacking the required privilege → 403. (e) A logged-out token is refused immediately.
Routes
POST /api/auth/login, POST /api/auth/logout, GET /api/sessions, POST /api/user/change-password, PUT /api/user/language, POST /api/users/{u}/unlock.
FR-2User & role administrationMUST

Administrators manage login accounts and the dynamic role catalogue, plus application settings.

Behaviour
CRUD users (username, role, email, phone, language, optional rep link). CRUD roles with a privilege array, default language/theme, and the six scope arrays. All writes pass the anti-amplification guard (§4.3). Application settings are a key/value store; secret-bearing keys are filtered from reads and masked on writes. A directory lookup endpoint returns non-credential user info for attribution (complaint assignment, sample-tracking).
Acceptance
(a) A user/role can be created, listed, updated, deleted with ManageUsers. (b) A caller cannot grant privileges/scope they lack. (c) A user cannot change their own role. (d) admin and in-use roles cannot be deleted. (e) Every write produces an audit entry.
Routes
GET/POST/PUT/DELETE /api/users…, GET /api/users/lookup, GET/POST/DELETE /api/setup/roles…, GET /api/settings, PUT /api/settings/{key}.
FR-3Laboratory managementMUST

Register and maintain client-lab accounts with their commercial, geographic, scheduling, contact, and media attributes.

Behaviour
Create/view/update/list labs within the caller's scope. A lab carries: unique code (case-insensitive), name, segment A/B/C, status (8-state set), geographic hierarchy (branch/governorate/city/area), payer & contract type, category, visit schedule (visit_times[], work_days[]), geo coordinates, images, encrypted-display fields, loyalty attributes (monthly target, points, tier), and collector/marketing rep assignments. Provide a next-code helper (GET /api/labs/nextcode) and a bulk image upload with content-sniffing validation (max 5 MB, type detected from bytes, GUID filename). Contacts are created/updated with the lab in one transaction. Creating/updating a lab may schedule its board intra-day. Optimistic concurrency: reads return a version token and updates return 409 on a stale version.
Acceptance
(a) Lab create/update/list/scope work; a duplicate code is rejected (BR-1). (b) Invalid input is returned as a single consolidated 400. (c) Next-code yields the next unused code. (d) Callers lacking ShowEncryptedLabs see encrypted labs under their ENC alias. (e) A stale update → 409.
Routes
GET /api/labs, GET /api/labs/{id}, POST /api/labs, PUT /api/labs/{id}, PUT /api/labs/{id}/status, GET /api/labs/nextcode, POST /api/labs/upload.
FR-4Representative managementMUST

Maintain field-rep profiles and their goals/targets.

Behaviour
Create/view/update/list reps within scope. A rep carries type (Collector/Marketing/Transfer/Scanning), salary, goal type, target, metric, and duration. Rep assignment to a lab is exclusive per assignment role (BR-4). Reads return a version token; updates are optimistic-concurrency guarded (409 on stale).
Acceptance
(a) Rep CRUD within scope. (b) A lab has one collector-assignment and one marketing-assignment at a time. (c) Stale update → 409.
Routes
GET /api/reps, GET /api/reps/{id}, POST /api/reps, PUT /api/reps/{id}.
FR-5Daily follow-up (collection board)MUST

Generate and operate the daily collection board: check-in, miss, undo, verify.

Behaviour
At Cairo midnight (and at startup) the board service generates today's board from each active lab's visit_times/work_days. A collector checks in a visit — recording a sample count (with a suggested value helper) — which may auto-create an outsource row and auto-update the lab's status, and broadcasts a real-time refetch signal. A visit can be missed (queues missed-visit notifications), undone (refused once collected/transferred), and verified by an elevated user (toggles the admin-checked flag). The board view unions today's board with history for context. Visit lifecycle: Pending → Visited | Missed, then Visited → Received at lab check-in (FR-7).
Acceptance
(a) A scheduled visit can be checked-in, missed, undone, verified. (b) Verify requires VerifyDailyFollowup; undo/miss require UpdateDailyFollowup; check-in requires AddDailyFollowup. (c) Undo of a collected/transferred visit → 400. (d) Every action writes an audit entry and is scope-checked.
Routes
GET /api/daily, GET /api/daily/{id}/suggest, POST /api/daily/{id}/checkin, /miss, /undo, /verify.
⚠ Build correction (JOBS-001). In the reference build the automated 22:00 "mark still-Pending visits as Missed" sweep does not fire on a continuously-running instance (the once-per-day guard trips at ~08:00 first). The rebuild must ensure the missed-visit sweep runs reliably at its scheduled time (e.g. a dedicated evening trigger independent of the morning birthday check), so missed counts are accurate and no Pending visit is archived as a terminal state.
FR-6Transfers & transportationMUST

Confirm hand-off of collected samples to a transfer rep / driver toward the hub.

Behaviour
List transferable items within scope; confirm a transfer by recording the transfer rep and driver details (name, mobile, car). Areas can be flagged as requiring transportation and carry a list of transfer reps. The confirm path re-fetches the target by id and re-checks scope and record ownership before acting.
Acceptance
(a) A collected visit can be transferred with driver details. (b) Confirm requires ConfirmTransfers or ManageTransfers and passes scope+ownership. (c) Writes are audited and broadcast.
Routes
GET /api/transfers, POST /api/transfers/confirm.
FR-7Lab check-in (receiving)MUST

Mark transferred samples as Received at the laboratory with a Cairo-time check-in stamp.

Behaviour
List items awaiting receipt; confirm receipt sets status Received, stamps the check-in time, and auto-updates the lab's derived status. Body-id operations re-fetch and re-authorize scope + ownership.
Acceptance
(a) A transferred visit becomes Received with a timestamp. (b) Requires ConfirmTransfers/ManageTransfers. (c) Audited.
Routes
GET /api/labcheckin, POST /api/labcheckin/confirm.
FR-8Sample tracking (per-area pipeline)MUST

Track per-area daily sample processing through a three-step pipeline with attribution.

Behaviour
For a given area and date, record data entry → review → sort, each capturing the acting user and timestamp. Support single and batch entry. Provide a lifecycle report. Scope is applied by area allow-list.
Acceptance
(a) Each step is recorded with user + timestamp. (b) Batch upsert works. (c) All operations require SampleTracking and are area-scoped & audited.
Routes
GET/POST /api/sample-tracking, POST /api/sample-tracking/batch, GET /api/sample-tracking/report.
FR-9Outsource samplesSHOULD

Track samples forwarded to an external destination lab.

Behaviour
Create an outsource record (unique per visit-date + lab) and advance its status Collected → Sent → Received. Delete supported. All scope-checked and audited. Check-in (FR-5) may auto-create an outsource row.
Acceptance
(a) Status transitions follow the fixed order. (b) One record per (visit_date, lab). (c) Requires OutsourceSamples.
Routes
GET/POST /api/outsource-samples, POST /api/outsource-samples/{id}/status, DELETE /api/outsource-samples/{id}.
FR-10Marketing visitsMUST

Schedule and record relationship/growth visits to client labs.

Behaviour
Create a marketing visit for one of seven purposes (pitch, renewal, complaint resolution, promotion, onboarding, reactivation, routine); complete it with an outcome, or cancel it. Lifecycle: Scheduled → Completed | Cancelled. Listings order Scheduled visits ahead of others (BR-10). Creation queues a notification.
Acceptance
(a) Create/complete/cancel work with the right privileges (Add/Update Marketing). (b) Scheduled-first ordering in lists. (c) Scope-checked and audited.
Routes
GET/POST /api/marketing, POST /api/marketing/{id}/complete, /cancel.
FR-11Complaint managementMUST

Log complaints against a client lab and move them through a controlled lifecycle with a full audit trail and an optional binding e-signature at resolution.

Behaviour
A complaint has a sequential id (CMP-<n>, BR-2), a category, a via-channel, an assigned team, and structured details. It carries two coordinated progression mechanisms: (1) a status machine — Open → {In Progress, Resolved}, In Progress → {Resolved, Open}, Resolved → {Open} (reopen) — enforced on the start/resolve/reopen actions, rejecting illegal transitions with 409; and (2) a staged investigation workflow (Logged → acknowledge → validity check → investigation/root-cause → business outcome → resolution & closure) captured in a stage field + details JSON. Every transition writes an audit row atomically. When electronic-signature enforcement is enabled, resolving a complaint requires a signature bound to the complaint's current state.
Acceptance
(a) Documented transitions are permitted; illegal ones → 409. (b) Each transition writes an audit entry atomically. (c) With e-signature enforcement on, resolve requires a valid bound signature. (d) All scope-checked.
Routes
GET/POST /api/complaints, POST /api/complaints/{id}/start, /resolve, /reopen, /stage, GET /api/complaints/{id}/audit.
Consistency requirement. In the reference build the /stage path can set status directly, bypassing the status machine and the e-signature gate. The rebuild should route all status changes through the single state machine so the e-signature resolve-gate cannot be skipped.
FR-12Loyalty & commissionsMUST

Compute lab loyalty points/tiers against monthly targets and rep commissions against achievement, plus the compensation configuration that drives them.

Behaviour
Loyalty: per-lab monthly ledger of points vs target; set a lab's target; recalculate. Commissions: per-rep monthly payout = base salary + commission + bonus, all recomputed server-side from targets vs achieved (client-supplied figures are ignored); Scanning-rep attribution joins the audit trail. Config: a compensation-configuration document defines the loyalty and commission formulas.
Acceptance
(a) Loyalty target set/ledger/recalculate require ManageLoyalty; body-id ops re-check scope. (b) Commission save requires ManageCommissions, recomputes every figure server-side, scopes per rep, and audits. (c) Compensation config read/write require ManageUsers or SetupRefs.
Routes
GET /api/loyalty, POST /api/loyalty/target, GET /api/loyalty/ledger/{labId}, POST /api/loyalty/recalculate, GET /api/commissions, POST /api/commissions/save, GET/POST /api/setup/compensation-config.
Scope requirement. The reference build does not scope the loyalty/commission/stats read endpoints (a user scoped to one governorate can read all figures). The rebuild should decide this deliberately — either treat these as organization-wide aggregates (documented) or apply org scope to the reads as the write paths already do.
FR-13Laboratory statisticsMUST

Maintain daily per-lab volume & income statistics via Excel import and Oracle sync.

Behaviour
Store daily per-lab registrations, test counts, and income keyed by date + lab code. Import from an .xlsx workbook (a hand-written spreadsheet reader), mapping rows to labs by mapping code; batch upsert; write a summary audit row noting unmatched/skipped rows. Oracle sync (FR-17) feeds the same tables.
Acceptance
(a) Import upserts by (date, lab_code) and reports skipped-unmatched rows. (b) Requires ViewLabStats. (c) Import writes a summary audit entry.
Routes
GET /api/labstats, POST /api/labstats/import.
FR-14Test catalogue & test statisticsSHOULD

Maintain the medical-test catalogue (groups & setups) and per-test daily statistics.

Behaviour
CRUD test groups and test setups (a setup belongs to a group; deleting a group leaves its tests ungrouped). Import per-test daily statistics from .xlsx. Reads require ViewTeststats; writes require the matching Add/Update/Delete privilege; every write is audited.

(a) Group/setup CRUD with correct privileges. (b) Test-stats import upserts by (date, test_code). (c) Writes audited.

FR-15Insights — dashboard & reportsMUST

Provide an operational dashboard and a set of management reports, all scope-filtered to the caller.

Behaviour
Dashboard: KPIs (active labs, open complaints, samples today…), today's schedule, unresolved complaints, per-rep attainment/progress, and birthday reminders. Reports: network overview (aggregates); rep performance (attainment + pace, on-track ≥ 85%, exposes salary); per-lab 360° history (ENC code shown for encrypted labs); rep cycle-time intervals. Attainment uses a rolling 90-day window; attainment/pace are engine-computed, never entered (BR-6/BR-8).
Acceptance
(a) Each surface returns data for the caller's scope only (via allowed-lab ids). (b) Report totals reconcile with the underlying records. (c) Requires ViewDashboard / ViewReports.
Routes
GET /api/dashboard, GET /api/reports/overview, /performance, /labhistory/{id}, /rep-intervals.
FR-16NotificationsMUST

Deliver templated bilingual notifications across in-app, mail, and WhatsApp channels, with per-user preferences and a real-time in-app feed.

Behaviour
Six seeded bilingual templates (complaint logged, complaint resolved, visit missed, marketing scheduled, pace alert, birthday). Channels: System (in-app), Mail, WhatsApp. Recipients addressed by username, by role:<Name>, or by R<n> (rep, WhatsApp-only). Per-user per-template channel preferences (default: system on, mail/whatsapp off). Encrypted-lab names are masked per recipient before rendering. The in-app feed is delivered in real time over SSE using single-use 30-second stream tickets (never the bearer token in a URL). Admins manage gateway settings (secrets masked), inspect the delivery log, and retry failed sends.
Acceptance
(a) A queued notification fans out to the right recipients and honors preferences. (b) In-app notifications arrive over SSE; the feed can be marked read. (c) Mail/WhatsApp sends are logged; failures can be retried. (d) Gateway secrets are never returned in cleartext.
Routes
GET /api/notifications, /{id}/read, /read-all, /stream-ticket, GET /api/notifications/stream, GET/PUT /api/notifications/preferences, /gateways, /logs, /logs/{id}/retry, DELETE /api/notifications/logs.
⚠ Build correction (JOBS-003). HTML email bodies must HTML-escape template variables (complaint description, lab name). The reference build injects them unescaped into an HTML body. Also add automatic delivery retry/backoff rather than manual-only retry (JOBS-006).
FR-17Oracle integrationSHOULD

Read-only synchronization of labs and statistics from the group's upstream Oracle system.

Behaviour
Exactly three allow-listed SELECTs (Labs, LabStats, TestStats) are executed; the SQL text and connection string are configuration-managed only (never web-editable) and re-validated at execution against the allow-list (fingerprinted). Only enable/disable and the interval are writable through the UI. A poll loop runs the sync per the configured interval (default 24 h) under an advisory lock; a manual "sync now" is also provided. Lab upserts apply documented defaults for fields Oracle does not supply and never overwrite locally-set scheduling/assignment on re-sync. The connection string is never returned by the API.
Acceptance
(a) Enable + interval are writable; any SQL/conn-string change via API → 400. (b) Only allow-listed queries run; a refused query is skipped and logged; all-refused is reported as "did not run", not success. (c) Requires OracleIntegration.
Routes
GET/POST /api/integration/config, POST /api/integration/sync-now.
⚠ Build correction (JOBS-002). The scheduled sync must write audit entries for the business data it mutates (labs/stats/income), matching the manual sync-now and the xlsx import. In the reference build the timer-driven path records only a status field, leaving automated mutations outside the append-only trail.
FR-18Reference data & setupMUST

Maintain the editable reference data the rest of the system depends on, plus the retention policy.

Behaviour
CRUD reference items (governorates, branches, marketing purposes, complaint categories, teams, channels, payers, contract types, lab categories), cities, and areas (an area carries transfer reps and a transportation-required flag). Renames cascade to referencing labs/cities/areas. Reads of reference lists are available to any authenticated user (dropdown data); writes require the matching setup privilege and are audited. Configure the data-retention policy (minimum 30 days; default keep-everything) and run an on-demand purge.
Acceptance
(a) Ref/city/area items can be listed, added, deleted; renames cascade. (b) Deletion behaves predictably (rejected or cascaded per rule). (c) Retention policy read/update/run require ManageUsers/SetupRefs; min-days validated.
Routes
GET/POST/DELETE /api/setup/refs…, …/cities…, …/areas…, GET /api/refs, GET/PUT /api/setup/retention, POST /api/setup/retention/run.
FR-19Electronic signatureSHOULD

Apply a binding, tamper-evident electronic signature to a record and verify it later.

Behaviour
A signer signs a record by re-authenticating (password), declaring a meaning (Authorship / Review / Approval / Verification / Execution), within organizational scope. The signature's record digest is computed server-side (the client never supplies it) and the signer IP is captured. Verification recomputes the digest and reports whether the record still matches the signed state (tamper evidence). In the reference build only the complaint module is signable. This capability underpins the optional complaint resolve-gate (FR-11).
Acceptance
(a) Sign requires re-authentication + scope; digest is server-computed. (b) Verify returns whether the current record still hashes to the signed digest. (c) Every signature is audited.
Routes
POST /api/esign/sign, GET /api/esign/{module}/{recordId}.
UI requirement. The reference build's sanctioned client exposes no e-signature UI (the capability is reachable only by direct API call). The rebuild must provide a user-facing signing flow if e-signature is to be a delivered feature.
FR-20Audit trailMUST

Maintain an append-only audit trail of every state-changing operation, queryable by administrators.

Behaviour
Every write records an audit entry (timestamp, actor username, entity, entity id, action, before/after JSON). The trail is immutable at the database level: UPDATE/DELETE/TRUNCATE are refused by triggers, binding even the table owner. The only permitted deletion is a bounded retention purge that (a) writes a summary audit row first and (b) deletes only rows older than a transaction-local declared cutoff — history can be expired under a recorded policy but never rewritten.
Acceptance
(a) Each state-changing route writes exactly one audit entry, atomically with the change. (b) Attempts to update/delete audit rows outside the retention path fail. (c) An administrator can query the trail (filtered) and a per-complaint audit view.
Routes
GET /api/audit, GET /api/complaints/{id}/audit.
FR-21Platform & healthMUST

Expose liveness/readiness/version endpoints and a guarded map short-link resolver.

Behaviour
Three anonymous health endpoints: liveness (no dependencies), readiness (DB round-trip; 503 on failure, wired to container/orchestrator health checks), and version (build version/commit). A single authenticated map short-link resolver fetches a Google-Maps redirect target with an SSRF guard (host allow-list, no auto-redirect, 5-second timeout) to help geo entry.
Acceptance
(a) Health endpoints are anonymous and dependency-appropriate. (b) The map resolver rejects non-allow-listed hosts.
Routes
GET /healthz/live, /healthz/ready, /healthz/version, GET /api/maps/resolve-redirect.

7 · Data requirements

The system owns a PostgreSQL schema of 31 tables across identity/audit, core business (labs/reps/contacts), operations (visits/marketing/complaints/transfers/tracking/outsource), statistics/catalogue/compensation, and reference/notification/integration groups. The full entity-relationship model, keys, constraints, and indexes are specified in Document 03 §Data model. Key data requirements:

  • Referential integrity: permanent archive (visit_history) and signed records use RESTRICT foreign keys so history and signers cannot be silently removed; dependent detail rows (contacts, ledgers, preferences) CASCADE with their parent.
  • Enumerations enforced in-DB: lab status (8), visit status (4), complaint status (3), marketing status (3), outsource status (3), rep type (4), signature meaning (5), etc.
  • Concurrency: optimistic concurrency on labs & reps via a row-version token (409 on stale). Other tables are last-writer-wins.
  • Money precision: all monetary columns are fixed numeric(18,2).
  • Auditability: audit_entry is append-only (triggers); retention purge is the only bounded exception.

9 · Non-functional requirements

9.1 Security

IDRequirement
NFR-SEC-1Default-deny: every mapped route must be declared in the policy table or be refused; unmapped /api/* routes return 403 and log critically.
NFR-SEC-2Server-authoritative authz: privileges and all six scope arrays are re-read from the database on every request (never trusted from the token); a missing role fails closed to empty scope.
NFR-SEC-3Passwords: PBKDF2-SHA256, 100k iterations, per-user salt, constant-time compare. Tokens: signed (HMAC-SHA256), ~10-hour expiry; signing secret from environment, fail-fast if missing.
NFR-SEC-4Login protection: per-account lockout + per-IP rate limiting; lockout state disclosed only to a valid-credential caller.
NFR-SEC-5Transport/headers: optional HSTS/HTTPS redirect; security headers (nosniff, frame-deny, no-referrer, COOP); CSP script-src 'self' (no inline scripts — markup carries actions, not code).
NFR-SEC-6Injection safety: all SQL parameterized; all HTML output escaped (including email bodies — FR-16 correction); file uploads content-sniffed and size-capped; SSRF guard on the map resolver.
NFR-SEC-7Secret redaction: secret settings are filtered from reads and masked on writes; the Oracle connection string is never returned.
NFR-SEC-8Anti-amplification on all privilege/scope grants (BR-12).

9.2 Privacy & data protection

NFR-PRIV-1. Complaint details can contain patient-identifying fragments (patient name, accession number, result value). These persist in the complaint record and are echoed into the append-only audit trail, and free-text complaint descriptions can egress to WhatsApp/SMTP. The rebuild must make a deliberate data-classification decision: either prohibit/segregate patient-identifying capture, or treat the system as holding protected data with the corresponding controls (encryption at rest, minimized egress, retention). Encrypted-lab names are already masked before egress; descriptions are not.

NFR-PRIV-2 — Personal data (staff/contact names, phones, birthdays, IPs) is retained under the configurable retention policy; sessions age from last activity.

9.3 Performance & scalability

  • NFR-PERF-1 — Interactive list/read endpoints respond within a few hundred milliseconds at seed-scale data; the performance behaviour warns on any use case exceeding ~1 s.
  • NFR-PERF-2 — All list responses are bounded (max page size 1000) and truncation is always declared in the envelope + headers, never silent.
  • NFR-PERF-3 — Scope filtering should be pushed into SQL (with an in-memory post-check) rather than reading whole tables; hot filter/FK columns should be indexed. (The reference build does this only partially — a documented scale item.)
  • NFR-PERF-4 — The system targets a single instance; horizontal scale-out requires a shared SSE/ticket store and is out of baseline scope.

9.4 Reliability & availability

  • NFR-REL-1 — Schema is provisioned/migrated at startup; migrations are tracked, transactional, and advisory-locked (run-once). Migration strictness is configurable (fail-fast vs continue-with-warning).
  • NFR-REL-2 — All four background jobs are singleton-guarded by advisory locks: a second instance skips rather than duplicating work.
  • NFR-REL-3 — Readiness endpoint gates traffic on DB connectivity; liveness is dependency-free.
  • NFR-REL-4 — Optimistic concurrency prevents lost updates on labs/reps.

9.5 Auditability & compliance

  • NFR-AUD-1 — Every state change is audited atomically with the change (FR-20); the trail is immutable at the DB level.
  • NFR-AUD-2 — Automated data mutations (Oracle sync, cron sweeps) are audited to the same standard (FR-17 correction).
  • NFR-AUD-3 — Electronic signatures are tamper-evident (server-computed digest; re-verification on read).

9.6 Usability, i18n & accessibility

  • NFR-UX-1 — Full English/Arabic bilingual UI with right-to-left support and a per-user language preference; bilingual notification templates and test catalogue.
  • NFR-UX-2 — Light/dark theming with a corporate token palette.
  • NFR-UX-3 — Accessibility: labelled controls and keyboard-activable interactive elements.
  • NFR-UX-4 — Consistent error presentation: one problem-details (RFC 7807) shape everywhere; a caller error is never reported as a server fault (400 vs 500 discipline), always with a correlation id.

9.7 Observability

  • NFR-OBS-1 — Structured logging (console + daily rolling file, retained ~14 days) with service/environment enrichment; every 401/403/5xx logged with its correlation id; request bodies never logged (they carry credentials/personal data).
  • NFR-OBS-2 — A single tracing source per use case and per background job (exporter optional).
  • NFR-OBS-3 — Build identity (version + commit) surfaced at startup and via the version endpoint.

9.8 Maintainability & portability

  • NFR-MNT-1 — Layered architecture (Domain → Application → Infrastructure → Api) with enforced dependency direction; see Document 03.
  • NFR-MNT-2 — Deterministic builds; dependency-vulnerability auditing in CI.
  • NFR-MNT-3 — The sanctioned client is dependency-free and needs no build step; asset cache-busting is CI-verified.
  • NFR-PORT-1 — Runs both containerized (Linux) and on IIS in-process (Windows); the only stateful dependency is PostgreSQL plus an uploads volume.
