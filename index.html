Purpose of this package

This package is a reconstruction-grade specification of the Follow-Up Management System. It is written so that a competent engineering team can build a functionally identical application from scratch — covering what the system does (requirements & rules), how the business flows through it (workflows & state machines), and how it is structured (architecture, module dependencies, data model, and interfaces). It is reverse-engineered from the running implementation and its as-built engineering review, then re-expressed as forward requirements.

System at a glance

Executive summary

The Follow-Up Management System is a single-tenant, bilingual (English/Arabic) B2B client-relations and field-operations platform for a medical-laboratory group (operator: Mega Laboratory). Its "clients" are other laboratories, not patients: the group's field representatives visit client labs on daily rounds to collect samples, transfer them to hubs, receive them at the laboratory, resolve complaints, run marketing visits, and track volumes and revenue. On top of operations it computes loyalty points for labs and commissions for reps, produces dashboards and management reports, and integrates read-only with the group's upstream Oracle system.

Architecturally it is one ASP.NET Core 8 service on port 5080 that serves both a zero-build vanilla-JavaScript single-page application and a JSON API, backed by PostgreSQL accessed through a hand-written wire-protocol client (no ORM). Four background jobs run in-process on a single instance behind PostgreSQL advisory locks, and real-time updates are pushed over Server-Sent Events. Authorization is enforced server-side in three layers: a default-deny route policy table, ~45 fine-grained privileges, and a six-dimension organizational scope plus record-ownership model.

Reading order. Start with Document 01 (SRS) for the "what", then Document 02 (Workflows) for the "how the business flows", and Document 03 (Architecture) for the "how it is built". Every requirement, table, and route in this package is derived from the actual implementation.

Build-quality note. This specification describes the intended target behaviour. A handful of known defects in the reference implementation (e.g. the automated missed-visit sweep not firing on a continuously-running instance, and unaudited scheduled Oracle syncs) are called out inline as ⚠ Build correction notes so the rebuild does not reproduce them.
